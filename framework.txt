### Framework conditions for the implementation 

- **Public-metadata only**: \toolname{} must base trust decisions on *publicly available* source-platform and package-registry metadata (commits/PRs/releases/contributor & governance metadata), **not** on source-code analysis.

- **Data-source assumptions**:
  - Projects use **public repositories** and **public registries** (no privileged access required).
  - At fetch time, platform/registry APIs return **accurate metadata**.
  - Repository history is assumed **complete/unchanged at first observation**; tampering **before** first observation cannot be detected later.

- **Threat / scope constraints (what implementation must and must not cover)**:
  - In-scope: **subversion of legitimate packages** via contributor abuse, maintainer takeover, release compromise, dependency injection, and (post hoc) **history tampering** signals.
  - Out-of-scope: **typosquatting / brand-new trojan packages**, **build pipeline / artifact verification**, and attacks without traces in governance/registry records.

- **Audit trail is the central artifact**:
  - Must record a durable, time-ordered audit log per project in five **event categories**: **Contributor**, **Governance**, **Release**, **Dependency**, **Integrity**.
  - Must be **append-only**: on later runs, only append new entries; do not edit/delete old entries.
  - Must support **dated state observations** (snapshots) when platforms don’t provide historical event streams (e.g., “current maintainer list”).

- **Integrity refetch capability**:
  - Must support an **optional, heavier** “integrity refetch” that re-reads public history and appends **integrity events** when the live platform view no longer matches previously recorded items (logical identity comparisons for commits/tags/PRs/releases).
  - Not required on every run; intended for higher-assurance checks and post-incident investigation.

- **Two audit modes + checkpoints (baseline handling)**:
  - **Initial audit**: build a *repository profile* from older history; compare a *recent tail* window against it (tail is defined as last \(W\) days, e.g. \(W=90\)).
  - **Re-audit**: append incrementally; compare *post-checkpoint* activity against the **stored profile snapshot** from the last acknowledged checkpoint.
  - **Checkpointing is explicit/manual**: findings do not auto-clear; baseline advances only when the developer acknowledges a report.

- **Metrics and detection are constrained by the audit trail**:
  - Only metrics that are (1) **threat-aligned**, (2) **actionable**, (3) **baseline/anomaly-based** (preferred over raw counts), and (4) **derivable from the audit trail** may be implemented.
  - Therefore, implementation must at least enable computation of the nine in-scope metrics via the audit trail:
    - **Contributor**: contributor identity, onboarding of new contributors, irregular commits
    - **Governance**: role changes, ownership changes
    - **Release**: unusual release pattern, unverified release publishers
    - **Dependency**: new dependency introduction
    - **Integrity**: history integrity
  - Metrics requiring external sources (e.g., **known vulnerabilities**, “missing security practices” inventories) are **excluded by design**.

- **Outputs the implementation must support**:
  - A **trust report** summarizing findings and deviations from baseline (for preventive assessment).
  - **Raw-data export** of recorded events for post-mortem timeline reconstruction.
